# Site

`atelier serve` is a read-only server over every Atelier repository on this
host ([ADR 0030](../adr/0030-a-read-only-site-a-session-database-and-t3-code.md)).
It serves each mission's brief and debrief, each repository's board, each
item and an inbox of what waits on the human as JSON, read from one captured commit of the repository's base branch,
never from a checkout, and writes nothing to any repository. The board's work
in flight is the one exception to reading only the base: it comes from each
owned work branch's own records, read at the branch's tip. The design is in
[the fleet-dashboard strategy](../strategies/fleet-dashboard.md) and decisions
atelier-c5vk and atelier-8p7u; this page says how the code does it.

## Crates

`crates/atelier-site` owns discovery, the routes, the cache and the load
limits. `atelier-cli` parses `atelier serve [--bind <addr>] [--root <dir>...]`
(defaults `127.0.0.1:7341` and `~/projects`) and calls `atelier_site::serve`,
so the site ships in the one `atelier` binary. The direction is
`atelier-cli` → `atelier-site` → `atelier-app`; the site never depends on the
CLI. HTTP is `axum` on a `tokio` runtime with two worker threads and at most
four blocking threads.

`crates/atelier-site/web/` holds the app (atelier-yn69, decision
atelier-8p7u): Vite, TypeScript, React, React Router and `react-markdown`,
managed with pnpm. Two of its directories are generated by the Rust tests and
not edited by hand: `src/api/`, the TypeScript types of every response, and
`src/fixtures/`, each route's response on the fixture repositories.

## Reading a repository at a commit

`atelier_app::commit_records::load` builds a `RecordIndex` from a commit's
tree in memory: it lists `.atelier/` through the read phase's
`git cat-file --batch` process (`ReadContext::files_under`), parses each blob,
and validates the records against the workflow policy and link types that
same commit holds (`RecordIndex::from_commit_files`). There is no temporary
directory, and the index names no repository, so no error message or
not-found lookup consults a checkout or another ref.

The brief and debrief views take a `ReadContext`. One made with
`ReadContext::at_commit(common_dir, commit)` reads one commit and nothing
else:

- `HEAD` is the captured commit, so `generated_from`, criteria marks, receipt
  ages and the history walks read it, not the common directory's `HEAD`,
  which is whatever the main checkout has out.
- Files such as the strategy are read from the commit's tree
  (`ReadContext::file_text`), for the brief's sections, the debrief's Why and
  the criteria.
- The history walk does not look for a fork from the base branch, since the
  commit is the base (`record_history::fork`).
- `code_clean` is true: a commit holds no uncommitted code.

A `ReadContext::new` made by the CLI reads the working tree and `HEAD` as
before, so `atelier brief` and `atelier debrief` print what they did.

## Discovery

`discovery::discover` walks each root, at most four directories deep, for
checkouts holding `.atelier/`. It does not descend into a checkout, hidden
directories, `node_modules` or `target`. Checkouts are grouped by
`git rev-parse --git-common-dir`, so a repository with several worktrees
appears once.

Each common directory is read from the checkout's `.git` as Git reads it: a
directory, or a `gitdir:` file naming a worktree's directory, whose
`commondir` file names the common one. `discovery::base` reads a
repository's base branch from refs and commits alone, with one
`git for-each-ref` in the common directory:

1. The default branch is the one `refs/remotes/origin/HEAD` names, else
   whichever one of local `main` and `master` exists.
2. The workflow policy committed on the default branch names the base branch.
3. If that is another branch, the policy committed there must name it too.

A repository with no default branch, with both `main` and `master` and no
`origin/HEAD`, whose base has no local branch, or whose base's policy names
another branch, shows that error in `/api/repos` and from its routes. Nothing
falls back to `HEAD` or a working tree.

A repository's name in URLs is the `project_slug` committed on its base,
else its directory name. In common-directory order, the first repository
with a name keeps it, and each repeat takes the first `<name>-<n>`, from 2,
that no repository has, so `demo`, `demo` and `demo-2` are served as `demo`,
`demo-3` and `demo-2`.

## API

Every route is a `GET` returning JSON. The bodies are `atelier-app` view
models serialized with `serde`, plus the base commit and links
(`crates/atelier-site/src/api.rs`):

| Route | Body |
| --- | --- |
| `/api/repos` | Each repository: base branch and commit, `atelier status`'s counts, and its missions, or the error that stopped them. |
| `/api/<repo>/mission/<id>` | One mission's id, title, status, category, links and `review`. |
| `/api/<repo>/mission/<id>/brief` | The `Brief` view `atelier brief` prints. |
| `/api/<repo>/mission/<id>/debrief` | The `Debrief` view `atelier debrief` prints. |
| `/api/<repo>/mission/<id>/strategy` | The strategy's path and Markdown as committed. |
| `/api/<repo>/board` | The `Board` view, the work in progress on each work branch, and the branches that cannot be read. |
| `/api/<repo>/item/<id>` | The `ItemView` of one item: its record's Markdown, where it stands, its links and the review events on it. |
| `/api/inbox` | What waits on the human in every repository, with its count. |

`review` is the one judgment the server makes: `brief` while the mission is
in its workflow's initial status, `debrief` afterwards, read from the
committed policy. A mission or item accepts a full or unique short ID, as the CLI
does.

### The board

`atelier_app::board::board` builds the board from a base commit's records,
from the same views the CLI prints:

- Open missions as `atelier work missions` orders them, each with its items
  done of planned and its criteria proven, as its debrief marks them
  (`criteria::mission_proof`).
- Open work under each open mission, then work in no open mission by label,
  as `atelier work missions` groups it, each list in `atelier work`'s order
  (`atelier_app::work_order`).
- Active, ready and needs-human work as `atelier status` and
  `atelier work ready` list it, with the ready gates `work ready` applies
  (`work_classification::apply_ready_gates`).
- Work closed on the day the server's clock says or in the 14 days before
  it, newest first.

`board::branch_work` reads one work branch as `atelier status` reads its
branch rows: a branch with no tracker, no owner, whose tip the base already
holds, or whose owners are done on the base, has no work in flight. Owners
are found by `branch_work::branch_owner_ids`, the function `status` uses;
the branch's records are loaded at its tip; and each owner's review state is
`review_gate::approval_state`, the judgment `status` and `merge` make, with
`unreviewed` when no review event targets the owner's scope. Open findings
are those `findings.disposed` would not count as settled. `board::in_progress`
lists the owners in branch order, then active work on the base that no
branch read owns.

### The inbox

`atelier_app::inbox::inbox` reads what waits on the human from a base
commit's records (atelier-uma8):

- Items: the work `atelier status` counts under Needs a human, from the same
  `status_view`, in its order. That is open decisions and ready work
  labelled `needs-human`, without the ready gates `atelier work ready` and
  the board's needs-human list apply.
- Each item's missions: every mission whose scope holds it, as
  `mission_overview` computes scope, and every mission it links under any
  role, among both its typed relations and its blockers, leaving out
  superseded and declined missions. A loose end, never in a mission's scope,
  reaches the mission it waits on through `blocked_by`. An item whose only
  mission is retired links only its own page.
- Draft missions: missions in their workflow's initial status that an
  approval targets, in `atelier work missions` order. An approval is what a
  planning review leaves, so a draft no one has reviewed stays off the
  queue.

The inbox is built with the records of each base commit and kept with them.
`/api/inbox` lists each repository that has an entry or an error, in
`/api/repos` order, each mission as `/api/repos` summarizes it, and `count`,
its items and drafts over every repository.

An unknown repository, mission, item, route or a mission without a strategy
is a 404, and a repository whose base or records cannot be read is a 500 naming
the error, from its own routes only; the others answer. Every error body is
`{"error": "..."}`.

The TypeScript types in `web/src/api/` come from the Rust types through
`ts-rs`, one file per type. `api::tests::typescript_types_are_current` fails
when they are stale. The fixture JSON in `web/src/fixtures/` is written by
`crates/atelier-cli/tests/serve/api.rs` from two fixture repositories built
with fixed dates, served on a clock fixed at 2026-01-10 (`SiteOptions::clock`),
and `fixture_responses_match_the_checked_in_json` fails when it is stale.
Rewrite both with `ATELIER_UPDATE_FIXTURES=1` and the same tests: the types
with `cargo nextest run -p atelier-site typescript_types`, the JSON with
`cargo nextest run -p atelier-cli --test serve fixture_responses`.

## Cache and load limits

Only work that depends on nothing but a base commit is cached: the records
loaded from it and each view built from them, as serialized JSON, keyed by
repository and base commit. A newer base commit replaces a repository's
entry, and a scan drops the entries of repositories that are gone, so only
the latest commit of each repository is kept. What the policy and config of
a default or base commit say is kept the same way. Only successes are kept:
a load, view or policy read that fails is tried again by the next request,
since the failure may be Git failing for a moment rather than the commit.
The views read a missing strategy as no strategy, so a read phase over a
commit tells a file the commit does not hold from one Git could not read
(`ReadContext::failed_read`); after the second, the view or the commit's
facts are an error, never kept, rather than a page that misstates the
commit.

The board is kept per base commit and day, since recently done work depends
on the date. Each work branch's work in flight is kept by repository and
branch, with the branch's tip and the base commit it was read against; a
scan drops an entry whose tip or base moved, or whose branch is gone. A
board request builds what is missing, the base's board and every work branch
not yet read, as one build each, so a warm board with nothing moved builds
nothing. Composing the in-progress list and an item view read only the
loaded records and take no build slot.

Refs are never cached. Every request scans the roots and reads each
repository's refs again, so it reads the base as of its arrival; requests
that arrive while a scan is running wait for the next one, which serves them
all.

A record load or view build runs on a blocking thread once it holds one of
two build slots, which it keeps until the work ends even if its request has
gone, and checks the cache again once it has one, so twenty
requests for the same cold view build it at most twice. A request that waits
more than five seconds for a slot gets a 503 with `Retry-After: 1`
(`builds_are_capped_and_a_long_wait_is_a_503`). The cap is a semaphore around
builds rather than a `tower` concurrency layer, so warm requests never queue
behind cold ones.

## Writing nothing

`Site::new` turns Git's optional locks off for every later Git command
(`git_freshness::read_only`, `GIT_OPTIONAL_LOCKS=0`). The server runs only
reading Git commands, in the common directory, where no index is refreshed.
`crates/atelier-cli/tests/serve/read_only.rs` makes every fixture
repository's working tree and `.git` unwritable and checks that every route
answers as before and that refs, the index and `git status` are unchanged.

## The app

The app lays out what the API returns and decides nothing about work. Its
routes mirror the API's:

| Page | Shows |
| --- | --- |
| `/` | Every repository, its base and counts, and a link to each mission, or the error that stopped them. |
| `/<repo>/mission/<id>` | The review the API's `review` names: the brief or the debrief. |
| `/<repo>/mission/<id>/brief` | What `atelier brief` prints. |
| `/<repo>/mission/<id>/debrief` | What `atelier debrief` prints. |
| `/<repo>/mission/<id>/strategy` | The strategy's Markdown, rendered. |
| `/<repo>` | The board: open missions with progress, work in progress with its branch, review state, open findings and how far behind, ready and needs-human work, open work by mission and label, and work done in the last 14 days. |
| `/<repo>/item/<id>` | An item's record as Markdown (a decision's Question and Options among its sections), its links and its review events. |
| `/inbox` | By repository, each needs-human item linking its page and its missions' pages (`Brief: <title>` or `Debrief: <title>`, by the API's `review`), then the draft missions to approve. |

The repository list links each board, the board links each mission and item,
and every page under a repository links back to its board. The repository
list and every board link `/inbox` as `Inbox (<count>)`.
An API error shows on the page; a 404 is a not-found page. Each page puts the
view's facts into the words the CLI uses (`web/src/debrief.ts` follows
`crates/atelier-cli/src/commands/mission_review.rs`). React escapes every
string. Markdown renders with `react-markdown`, raw HTML skipped, and one URL
policy (`web/src/components/Markdown.tsx`): relative paths, fragments,
`http`, `https` and `mailto` are kept as links and images, and any other
scheme renders as plain text.

### Serving it

`src/app.rs` embeds `web/dist` with `rust-embed`. Any path outside `/api/`
naming an embedded file gets that file with its content type, a missing path
under `/assets/` is a 404 (never `index.html`, so a stale page fails loudly),
and every other path gets `index.html`, so the app's router serves deep links.
Vite names each file under `assets/` by its hash, so those are cached for a
year and `index.html` is never cached.

### Building and shipping it

`crates/atelier-site/build.rs` decides what is embedded:

- A release build (`cargo install`, `cargo build --release`, `dist`) runs
  `pnpm install --frozen-lockfile` and `pnpm build` in `web/` when `web/dist`
  is missing or older than the app's sources. Without pnpm on `PATH` it fails
  naming the missing step, so no release binary ships without the app.
- A debug build embeds `web/dist` if it exists and never runs pnpm, so
  `cargo build` and `cargo nextest run` need no Node. Without `web/dist`, every
  page outside `/api/` says how to build the app.

`dist` runs the same `build.rs` for each target. Its runners get Node and pnpm
from the steps in `.github/build-setup.yml`, which `dist-workspace.toml`'s
`github-build-setup` names; `.github/workflows/release.yml` is regenerated
with `dist generate`, never edited by hand. The app is the same JavaScript
on every target, so cross builds (musl, aarch64) build it on the runner's host.

### Developing it

Install Node.js and pnpm (`corepack enable pnpm`; `package.json` names the
version). Then, in `crates/atelier-site/web/`:

```bash
pnpm install --frozen-lockfile
atelier serve &                # or target/debug/atelier serve
pnpm dev                       # http://localhost:5173, reloading on save
```

`pnpm dev` proxies `/api` to the `atelier serve` that `ATELIER_SERVE` names,
by default `http://127.0.0.1:7341`, the server's default address. To see the
app in a debug binary, run `pnpm build` and then `cargo build -p atelier-cli`.

### Testing it

In `crates/atelier-site/web/`:

- `pnpm typecheck` and `pnpm test` (Vitest and Testing Library) render each
  page from the fixture JSON in `src/fixtures/`, so the components are tested
  against real API output.
- `pnpm e2e` (Playwright) builds the fixture repositories with the ignored
  Rust test `write_fixture_fleet`, serves them with `target/debug/atelier`
  (`e2e/serve.sh`; `ATELIER_BIN` names another binary), and loads every route
  at a 390 px viewport, checking for console errors and horizontal scroll.
  Run `pnpm build` and `cargo build -p atelier-cli` first, and once
  `pnpm exec playwright install chromium-headless-shell`.
- `pnpm exec playwright test -c playwright.host.config.ts` loads every
  mission's brief and debrief, and every page the inbox links, from a
  running server over this host's repositories, named by `ATELIER_SERVE`.

CI's `web` job (`.github/workflows/ci.yml`) runs all but the last on every
change the Rust jobs run for, and on every change to `web/`
(`scripts/ci-jobs.sh`).

## Running it as a service

`crates/atelier-site/systemd/atelier-serve.service` is a systemd user unit
that runs the installed `atelier serve` on `127.0.0.1:7341` over `~/projects`,
restarting on failure and capped at one core and 1 GiB (`CPUQuota=`,
`MemoryMax=`) so T3 Code on the same host stays responsive. Install it:

```bash
mkdir -p ~/.config/systemd/user
cp crates/atelier-site/systemd/atelier-serve.service ~/.config/systemd/user/
systemctl --user daemon-reload
systemctl --user enable --now atelier-serve
loginctl enable-linger "$USER"   # keep it running after logout
```

The service runs the binary it started with. After each
`cargo install --path crates/atelier-cli --locked`, restart it:

```bash
systemctl --user restart atelier-serve
```

Publish it on the tailnet with `tailscale serve` on a port of its own, so
T3 Code's published ports stay as they are. Check which ports are taken
first, then add the site's:

```bash
tailscale serve status
tailscale serve --bg --http=7341 http://127.0.0.1:7341
```

The site is then at `http://<host>.<tailnet>.ts.net:7341/`, on the tailnet
only. `tailscale serve --http=7341 off` removes it.

## Naming a page from the CLI

`atelier brief` and `atelier debrief` end with the mission's page on the
site, `Send the human the page: <site>/<project_slug>/mission/<id>/brief`
(or `/debrief`), when the user has set the site's address. The address is
the first line of `site-url` in `$XDG_CONFIG_HOME/atelier/`, else
`~/.config/atelier/`, one file that every repository and harness on the host
reads without any environment to pass along:

```bash
mkdir -p ~/.config/atelier
echo "http://<host>.<tailnet>.ts.net:7341" > ~/.config/atelier/site-url
```

With no file, an empty one, or no readable `project_slug`, the footer names
no page. The CLI names the repository by its own `project_slug`, so a
repository whose slug another one on the host also uses, which the site
serves as `<slug>-<n>`, gets a URL for the other one.
