# Strategic Plans

Use a strategy document for a long-running, multi-epic, cross-system, or
tradeoff-heavy mission. Strategy is governing intent, not a backlog.

It owns the finished outcome, target system, governing decisions and tradeoffs,
boundaries, adaptation authority, and mission-level assurance. If the issue
graph could be rebuilt without changing a statement, that statement probably
belongs in strategy. User stories and independently managed requirements belong
in tracker records, not as anchors in the strategy document.

Use one stable repository path and a visible revision. Link it from the mission.
Revise it when the outcome, target system, governing tradeoff, boundary,
assurance, or adaptation authority changes. Use version control for exact
history rather than snapshot files.

Plan the whole mission as outcome-bearing epics. Product-facing and internal,
behavior-preserving outcomes use the same epic type. Keep distant epics in
draft; expand ordinary issues only through the nearest evidence boundary. When
evidence justifies the next increment, refine its outcome and preservation
claims, create immediate work and dependencies, choose proof, and make it
ready. Replan the graph directly within strategy authority.
