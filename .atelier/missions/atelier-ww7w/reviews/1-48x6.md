## Finding 1: `log::history` cannot supply the events the Desk's contract needs, and js4a may not change it
Recommendation: fix now
`atelier-js4a` says to translate `Logged` into `HistoryEvent` with the contract intact, and its Scope has no file of `atelier-core`. `Happened` (`crates/atelier-core/src/log.rs:70-131`) has no action for a mission being planned or for a plan's merge: `Walker::merge` reads only `item_path(id)`, and other merges "give nothing" unless they carry a skip.

On this repository the subject rules find 14 `planned` events and 6 mission `merged` events. `atelier log` finds no planned action and one mission merge, atelier-kw8u's, and only because that merge carried a skip. The consumers depend on exactly these events:

- `desk/src/pages/ProjectHome.tsx:136` and `t3-extension/src/home/model.ts:97` draw "Plan agreed" from a mission's `merged`.
- `desk/src/pages/MissionControl.tsx:309` and `t3-extension/src/mission/model.ts:223` date the plan's merge from it, and the extension starts a done mission's lanes there.
- `desk/src/lib/mission.ts` draws "Mission planned" from `planned`.

So "Plan agreed" would vanish from both homes, with no error. History from before the 0.5 cutover goes too: the log's first line is 2026-11-11T15:20:09Z, and 203 of the 279 non-mission IDs the subject rules show as merged have no merge in it.

"Bounded in execution time" also needs the core: `log::walk` calls `git::listing` with no deadline, where today's read runs under `bounded::run` with 15 seconds. (Speed itself looks fine: `atelier log` takes 0.4 to 0.7 seconds here.)

Put `crates/atelier-core/src/log.rs` in Scope with the new actions and the bound, say which Git fact gives each `EventKind`, and say whether losing pre-cutover history is accepted. If the core is to stay shut, this item cannot drop the parser.

## Finding 3: `merge` can never delete the local branch, because it always runs on that branch
Recommendation: fix now
clean-branches-and-drop (b), the design and `atelier-gqtw` delete the local branch "when `git::checkout_of` returns `None`". It never does. `read` refuses any checkout not on the item's, mission's or backlog branch, and `moved` (`crates/atelier-cli/src/merge.rs`) requires that checkout to still have the branch out at `head`. I confirmed both: from the base `merge` is refused, and after a successful merge the branch is checked out in the caller's worktree, where `git branch -d` fails with "used by worktree".

So this code path is dead, its test cannot be written, and the 285 local branches keep growing. Decide what should happen: detach the caller's checkout and then delete, or drop the claim and leave local cleanup to the hint. If it deletes, `git branch -d` is also the wrong test of merged, since it compares with the upstream or the current HEAD and not the base: from a detached HEAD behind the base it refused a merged branch. `git::delete_branch(repo, name, at)` already deletes only at a given commit.

## Finding 4: deleting the remote branch loses a late push, and AGENTS.md forbids it
Recommendation: fix now
`git push <remote> --delete <branch>` deletes whatever the branch holds at that moment, not the head that merged. In a scratch remote, a commit pushed after the head was read was deleted with exit 0. Reviewers push to these branches by design (`HEAD:refs/heads/<mission>`, retried after a pull), so a second review or a filed record can arrive there late. `--force-with-lease=<branch>:<head> --delete` refused the same race with "stale info". The Done when should require the lease and a test of the race.

`AGENTS.md:71` also says "Never force-push `master` or delete remote branches without the human." This change makes every `merge` in every repository the binary serves do so, and a revert does not bring the refs back. Neither the Authority nor the Why says Sumeet lifted that rule, and `atelier-gqtw`'s Scope has no `AGENTS.md`. Get and record that word, and change the line in the same item. `docs/design.md:1123` ("The branch is kept") changes with it.

## Finding 11: the "safe cleanup command" in status is unspecified and would hit live worktrees
Recommendation: fix now
`atelier-gqtw` prints a cleanup command once five detached worktrees exist, and never says what makes it safe. Every plan reviewer works in a detached worktree by instruction, and a merged, clean one is indistinguishable from an abandoned one. Of this clone's 64 detached worktrees, 3 have uncommitted work and 1 is at a commit not in master. Removing the last kind can leave a reviewer's commit unreachable. `status` runs at every session start and agents run the commands it prints.

Print a command that only lists (`git worktree list`, `git branch --merged <base>`), or define exactly what may be removed and test a live reviewer's worktree against it. With 64 and 119 against thresholds of 5 and 10, the notice would also be in every session here until a human acts. And "merged local named branches" leaves out 165 of the 285 branches the Why counts, which are `t3/*`: either count them or stop citing 285.
