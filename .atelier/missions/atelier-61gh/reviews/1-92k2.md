## Finding 1: Define current work in the thread lookup before using it to choose a page
Recommendation: fix now

`.atelier/items/atelier-prx5/item.md:31` requires the new lookup to use the same map as `/api/threads`, while `.atelier/items/atelier-knx8/item.md:31` requires navigation to prefer a started item, then an open review, then a mission. The existing map cannot make those distinctions. `crates/atelier-desk/src/read.rs:424` collects every implementer and every review's reviewers, and `holds` at line 470 collects those associations across every item and mission without filtering terminal records or superseded holders. `Hold` in `crates/atelier-desk/src/api.rs:465` carries only repository, kind, ID and role, with no status or current-holder information.

For example, a thread that implemented a completed item and now reviews another item is associated with both. Returning that map as specified leaves the consumer unable to tell that the implementer association is historical and the review is current. A replaced implementer is likewise still present. The frontend's stated precedence therefore needs information that its prerequisite does not promise, and a thread with only historical associations has no specified destination.

Amend the two items to define current versus historical associations, assign the filtering or additional metadata to the lookup item, and specify the historical-only fallback. Require a test with an old completed or superseded association alongside a current review or item, asserting the chosen destination. Keep historical associations available to existing consumers if they need them; the new navigation must not infer current ownership from role alone.
