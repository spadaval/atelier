## Finding 1: Start the next run at the previous measurement cutoff, not its merge
Recommendation: fix now

`.atelier/items/atelier-9dku/item.md:29` starts a run at the previous garden item's merge. But lines 27 and 34 take the numbers before review and then wait for a human session before merging; line 54 expressly permits that approved wait. The plan gives no refresh step or other handling of the intervening work.

For example, a gardener takes its numbers Monday, a product item merges Tuesday, and the session merges the garden item Wednesday. Tuesday's item was absent from Monday's input, and the next run starts Wednesday. Its durations, rounds and other contributions are never reported. The longer the session waits, the larger the silent gap. This defeats the successive-window comparison even when each run's arithmetic is correct.

Record an explicit measurement cutoff in the page and start the next run from that cutoff, with a stated boundary convention so items are counted once. Keep the garden merge as the way to locate the last completed report, rather than as its data cutoff. Require the procedure's worked example to account for an item merged between measurement and the garden merge. Update the mission design's corresponding window rule too. This needs only procedure and report text, not a new command or a full snapshot.

## Finding 2: Do not substitute change volume for the promised rework hotspots
Recommendation: fix now

`.atelier/items/atelier-9dku/item.md:57` specifies the files most changed in the window as change hotspots, while its page requirement at line 33 refers to the mission design's table. That table, `.atelier/missions/atelier-295u/design.md:129`, requires files with the most rework. `docs/product.md` defines rework as lines deleted within two weeks of being written, not files with the most changes. Line 55 of the item also says rework is carried from its last measurement, rather than measured in a routine run.

A large additive feature can lead a change-volume ranking with no rework at all, while repeated deletion of recently written lines can make a smaller file the actual rework hotspot. An implementer cannot fulfill both instructions by treating these rankings as interchangeable, and the resulting page could direct proposals at ordinary feature work as if it were waste.

Align the item and mission design on what is available. For the bounded routine run, explicitly call any fresh ranking change volume, and carry dated rework hotspots when available or use the page's existing unavailable-with-reason provision. Alternatively specify a real rework computation if that cost is intended. Preserve the product's definition and make the distinction explicit in the planned template; do not silently relabel change volume as rework.
