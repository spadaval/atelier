## Finding 1: Preserve frozen Git inputs when replacing the scorecard history readers
Recommendation: fix now

`.atelier/items/atelier-x3n5/item.md:29` requires running `atelier log` in each repository and discarding lines after the manifest cutoff. But `.atelier/items/atelier-8b0a/item.md:28` makes that command read the current base and current started-branch tips, and line 38 allows no revision selector. A time filter does not freeze those inputs. For example, an unmerged branch that existed before the cutoff can later be dropped and deleted; its pre-cutoff acts then disappear from the same rerun. Fetching additional history with older commit times can instead add lines. Mission membership used by `log <mission>` can also change after the snapshot.

The existing contract in `scripts/scorecard/README.md:57` reads each repository at its manifest commit specifically so a later checkout produces the same numbers; `counted.py` and `draw_samples.py` pass those commits to their readers. The proposed replacement drops that guarantee while the other measurements still read the fixed commit. This matters for the two-week comparison, not just for reproducing the old baseline.

Choose and document a fixed input for the new reader before its producer and consumer are built. For example, freeze the exact log output with the new snapshot and have the scripts consume that artifact, or run the command in an isolated repository with explicitly pinned base and branch refs. Specify which history belongs to the measurement and add a fixture proving that advancing the live base or deleting a branch does not change a rerun from the same manifest. This can be done without adding a new command or output mode.

## Finding 2: Keep record-only merges out of the baseline's counted-item population
Recommendation: fix now

`.atelier/items/atelier-x3n5/item.md:26` defines the window's merged items as the log's `merge` lines. Those lines include an Atelier merge that changes only `.atelier/` records: the log definition in `docs/design.md:860` tests the status transition and merge commit, not whether product files changed. Neither this item nor the log's output contract retains the existing exclusion.

`scripts/scorecard/README.md:104` and `docs/architecture/quality/scorecard-baseline-2026-11.md:192` explicitly define the counted population for process share, tokens per merged item and calls before first edit as items whose work changes a file outside `.atelier/`. `records.py:merged` enforces that restriction today. Replacing it with all merge lines admits record-only planning or gardening work and changes the population underlying the before/after comparison. The item mentions changed thread-tie coverage at line 49, but not this separate change of population; the mission's Authority also forbids changing a measure's definition.

Use the merge lines to identify candidate items, then preserve the outside-`.atelier/` change test using the named merge commit's diff against its first parent. That is a product-diff check, not another walk of record history. Explicitly permit it in the script item's scope and require a fixture containing both a product merge and a record-only merge, with only the former included in these counted measures. If a broader population is desired instead, obtain a decision changing the measurement contract before implementation and state how the comparison will remain meaningful.
