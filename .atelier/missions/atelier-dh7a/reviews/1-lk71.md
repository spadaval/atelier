## Finding 1: Item draft/ready as open must not agree old mission drafts
Recommendation: fix now

The Outcome says records written before the change still read, with `draft` and `ready` both as `open`, in this repository and every other the binary serves (`mission.md`, Outcome). That sentence does not say *item* records. The five served repositories still store the old mission form: astromech has three `status: ready` missions, life-on-rails one `draft` and two `ready`, cosplay-studio six `draft` and one `ready`, demiurge and worldcrafter one `draft` each. This repository's atelier-to83 is still `status: ready`.

Today those values are not item statuses. `MissionStatus` already reads YAML `ready` as `open`, and keeps `draft` as a distinct proposed state that cannot be led or have its items started (`crates/atelier-core/src/model/mission.rs` 41–56, 64–70; `docs/design.md` 208–221). The action table encodes that proposed state as item `Status::Draft` and an agreed mission as item `Status::Ready` (`mission.rs` 64–70). If item `draft` and `ready` both become `open`, and that mapping is reused, an old mission `draft` becomes agreed without two plan reviews, which is the failure `docs/design.md` 218–221 exists to prevent.

atelier-v06d's Done when says "everywhere the binary reads items", which is the right scope. Put that bound on the Outcome and on old-records-read: item `draft` and `ready` read as `open`; the old mission form is unchanged (`draft` stays proposed, `ready` stays `open`). Name the action-table encoding so v06d retargets `MissionStatus::status()` without collapsing `MissionStatus::Draft`.

## Finding 2: Filing on an item's branch still un-approves that item
Recommendation: defer

`atelier new` is refused on an item's branch because the write sits outside that item's directory and would make a review of it stale (`crates/atelier-cli/src/plan.rs` 59–62, `Belongs::Backlog`; `crates/atelier-core/src/say.rs` 512–518). Merge already treats another item's record that way: `a_change_to_another_item_after_approval_makes_it_stale` in `crates/atelier-cli/tests/merge.rs` 311–316, from `actions.rs` 1062–1085.

atelier-u6oy wants a commit that only adds an item's record not to stale the parent approval, or a Report that says why it must stale and what the reviewer does instead. atelier-8phx then tells every role, the reviewer in the implementer's checkout included, to file on the branch they are on. The implementer path is fine: file before `submit`, and the review covers the extra record. A reviewer who files after `verdict approve` hits today's stale check and cannot merge until another round. If the Report's alternative is "file on a backlog branch", it contradicts 8phx and file-where-you-are.

Pick one rule in the plan: a new item record on an item's branch does not stale that item's approval, and a test holds it; or 8phx says a reviewer files after the parent merges, or on a backlog branch when they hold no `start`-made branch. Do not leave both items to invent it.
