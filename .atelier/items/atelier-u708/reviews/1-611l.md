## Finding 1: Native Codex child usage limits are lost and become reusable task failures
Recommendation: fix now

`evals/agent-factory/harness/run.py:889-898` checks the first agent's stream and the child transcripts in `threads/`. For the `sol` setup, however, `codex_thread_events` at lines 714-743 retains only `event_msg/item_completed` records and unconditionally appends `turn.completed`. A child's raw `event_msg/error` is discarded. The parent's completed collaboration-tool item is also not examined by `provider_limit`, and a later normal parent reply clears its own limit state. A native child's failure therefore does not become a top-level parent error as the README assumes.

I used `RunOneTest`'s stand-in agent with the real `run_one` path and `sol`, adding a child rollout with valid model/effort metadata and an error saying "You've hit your usage limit." The parent reported the errored child in a completed collaboration item and then completed its own turn. The generated child transcript contained only `turn.completed`; `run_limit` and `thread_problem` returned no problem. With failed task facts, `run_one` produced `pass: false`, no invalid reason, and parent exit 0. `kept_runs` then kept that result instead of retrying it. Thus the capacity failure permanently contributes a task failure on the very setup used by the matrix.

Read terminal provider failures from native children's raw session records, or preserve those failures faithfully in their converted transcripts. Test the full native-child path, including a parent that finishes normally after its child hits a limit, and a child that later recovers. Such a run must be null with the provider's reason and eligible for retry.

## Finding 2: Reuse compares the setup name instead of its actual roles and judges
Recommendation: fix now

`evals/agent-factory/harness/run.py:1212-1229` accepts any graded result whose `setup` string matches. Although results already contain `roles` and `judges`, neither is compared with the requested setup. Editing `setups/sol.json` or `setups/house.json` therefore leaves old grades silently reused under the new configuration.

In a model-free `MainTest` reproduction, I wrote a graded result with `sol`'s current roles at `high`, then loaded a temporary `sol.json` with the same roles at `xhigh`. Running `main --setup sol` printed `{"kept": 1, "making": 0, ...}` and started neither a run nor a canary. The table presented the old grade as the requested matrix. Changing a judge under the same setup name has the same problem. This contradicts the Report's guarantee that a kept run is in the same setup and prevents an otherwise identical matrix command from evaluating a setup edit.

Pass the resolved setup into the reuse check and require its relevant role and judge specifications to match the saved result. Add a regression that changes a role or judge while preserving the setup name and confirms the affected runs are made again.

## Finding 3: Table aggregation mistakes independent matrices for retries
Recommendation: fix now

`evals/agent-factory/harness/table.py:37-46` deduplicates null results by only setup, scenario, arm and index after `read` has concatenated all input files. Every independent matrix starts its indices at zero, so a result in another output directory can erase a legitimate invalid sample. The README tells users to use another `--out` to sample again, and the table command supports multiple outputs, so these are distinct runs.

For two records with the same logical key but run directories `/matrix-a/run` and `/matrix-b/run`, where A is null and B passes, `table.rows([a, b])` reports null 0. Reversing the same records reports null 1. The first matrix was never retried, and changing CLI input order should not change its invalid count. This also suppresses repeated null samples across independent output files.

Keep retry suppression local to each results file/output matrix, or carry a matrix identity through aggregation and include it in the key. Cover both orders of two independent matrices and retain the existing same-output retry behavior.

## Finding 4: Concurrent server smoke tests can still collide on one host port
Recommendation: defer

The Report correctly discloses this limitation. `evals/agent-factory/scenarios/refused-push/setup.sh:51-55` produces a server that binds port 8080 unless `PORT` is set, while `agent_env` in `evals/agent-factory/harness/run.py:497-516` provides no per-run port or network namespace for this unconfined case. If two agents smoke-test `python3 server.py` while their runs overlap, one receives an address-in-use failure or can query the other run's server. Separate work directories cannot prevent it.

This is a real remaining source of interference, also possible between separate matrices before this change. It is documented, the fixture's normal unit test only imports the server, and the benchmark did not encounter it, so I would not block the concurrency change on network isolation. Track a follow-up for per-run server endpoints or network isolation and a model-free overlapping server test.
