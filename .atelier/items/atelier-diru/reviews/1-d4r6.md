## Finding 1: Isolate OpenCode's directory discovery as well as its environment
Recommendation: fix now

`t3-extension/t3-instance.mjs:43-49` replaces HOME and XDG paths, but OpenCode can
still discover the caller's and the real home's files. The `execFileSync` calls
at lines 185-190 inherit the caller's working directory. I invoked the same
`opencode models --standalone` probe with an empty replacement HOME/XDG tree and
a throwaway working directory containing an `opencode.json` provider with a
fake API key, a loopback endpoint and a model with nonzero cost. Its output
included `reviewfake/paid-test-model`. Line 287 would therefore accept that
paid, configured model as free. No paid request or real credential was used in
this reproduction.

There is a runtime leak too: after a normal start, the instance's
`home/.local/share/opencode/log/opencode.log` reports both `watcher subscribe`
and `watcher started` for the real `~/.claude/skills` and `~/.agents/skills`,
plus probes of the real `~/.opencode/skill` and `~/.opencode/skills`. Those paths
are outside the replacement home. The isolation check only guards the three
paths at line 412 and samples current file descriptors, so it reports success
without catching this access. The claim that OpenCode reads none of the human's
folders is not established by replacing its environment.

Prevent caller/project/ancestor discovery from reaching the human's
configuration and skills for both the probes and T3's OpenCode service, and
extend verification to catch this case. In particular, a model list contaminated
by caller configuration cannot be used as proof that a model needs no credential
or payment.

## Finding 2: Serialize starts before deleting the shared instance directory
Recommendation: fix now

`t3-extension/t3-instance.mjs:270-284` checks state once and then recursively
removes the shared instance directory, without a startup lock. State is not
written until line 295, after home creation, OpenCode model discovery and display
startup. Two overlapping starts can both see no state and then delete or modify
the same home while the other command is using it. Port checks do not protect
this window, since no T3 process has bound its ports yet.

I spawned two unchanged `start` commands together against the default root. One
failed in `opencode models --standalone` with `Standalone server exited before
reporting readiness`; the other completed. This is a real failure of the shared
instance lifecycle, not a missing dependency: the sequential start and reuse
passed. A different interleaving can overwrite process state or remove files
from an instance that the other command has just launched.

Acquire exclusive ownership before checking state or clearing the directory,
and make another start reuse or wait for the startup already in progress. Keep
that ownership until the complete instance state is available so the second
command also cannot call `describe()` on the partially written state.
