## Finding 1: Fall back to the inbox when the repository-list fetch rejects
Recommendation: fix now

In `desk/src/components/Shell.tsx:144`, the new `await read<ReposResponse>(api.repos())` shares the outer catch at lines 153-155 with the ties read. A non-OK HTTP response returns null and reaches the inbox fallback, but a connection reset or rejected JSON read jumps to that catch and skips `place` and navigation, even though the new thread's ties were successfully read. The Desk silently keeps the previous thread's page, with no explanatory line. Repeating the same `host:thread` cannot recover it because those messages are intentionally ignored.

Reproduced on desktop and phone with the existing host fixture: first send `host:thread` for `tied.implementer` and wait for `/embed/r/atelier/item/atelier-uwxy`; intercept `**/api/repos` with `route.abort("connectionreset")`; then send `{ type: "host:thread", thread: tied.none, repository: "atelier" }`. The ties request succeeds, the repository-list request is attempted, and the URL remains `/embed/r/atelier/item/atelier-uwxy` instead of `/embed/inbox`. Returning HTTP 503 from the same interception correctly reaches `/embed/inbox` and shows "This thread holds no open work."

This contradicts the Report's failed-list fallback and `docs/architecture/desk.md:405` (the inbox when the list cannot be read), and makes a new thread retain unrelated work. Handle rejection of the repository-list read locally so a failed list still reaches `place(body.ties, null)`. Preserve the existing behavior when the ties themselves cannot be read, and add a host contract test for a rejected repository-list fetch after a thread switch.
