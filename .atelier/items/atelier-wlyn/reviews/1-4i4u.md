## Finding 2: Keep the download operation and URL when reading the response body fails
Recommendation: fix now

`t3-extension/t3-custom.mjs:113-114` reads the zip and checksum bodies outside `get`'s error wrapper at lines 84-88. Fetch resolves when headers arrive, so a connection reset or timeout during arrayBuffer()/text() bypasses that wrapper. With a local server returning HTTP 200 and Content-Length: 100, writing a partial zip, then destroying the connection, `update` exited 1 and recorded `error: "terminated"`. A running injector with autoUpdate on reported the same string in status.update.error, with lastError still null and release 0.1.0 unchanged. The page formats that as `Release check failed: terminated`.

This is a failed download without its operation, asset or URL, contrary to the named-failure criterion and the extension's guidance on actionable errors. Wrap body consumption as well as fetch with the download's operation and URL, retain the underlying reason, and cover an interrupted response in the fixture tests. Do this for both the zip and checksum.

## Finding 3: A release outside the first 100 results becomes invisible to the updater
Recommendation: defer

`t3-extension/t3-custom.mjs:69,91-102` fetches one page of the repository's combined release list and never follows pagination. Once 100 newer Atelier releases follow the last extension release, a device on an older extension is told no extension release was published, even though a newer one exists on the next page. This limitation is disclosed in the Report, and does not block the first extension release. Track following GitHub's next-page link or otherwise enumerating all matching extension releases before the shared release history can reach that state.
