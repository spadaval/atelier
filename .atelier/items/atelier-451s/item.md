## Goal

Let the extension be released as often as it changes, without releasing
`atelier`. Sumeet wants a bundle a device downloads, published from a tag of
its own.

## Done when

- [x] A workflow publishes a GitHub release when a tag `t3-extension-v<version>` is pushed, where `<version>` is three numbers. It builds no Rust and runs no test itself: before publishing it finds the tested commit and refuses the tag unless that commit's CI run concluded success with the extension's job run in it and not skipped. The tested commit is the newest commit on `master`'s first-parent history, at or before the tagged one, that changes a path the extension's job runs for, by the rule in `scripts/ci-jobs.sh`. On `master` CI compares each merge with the one before it, so a later merge that touches none of those paths skips the job; such a merge changes nothing the job tests, and a tag on it is accepted on the strength of the tested commit. The workflow reads the rule from `scripts/ci-jobs.sh` and does not keep a second copy of the path list. It builds one bundle holding the extension's files and its installer, and attaches the bundle and its SHA-256 checksum. The bundle carries its version in a file the installed extension reads.
- [x] The release is not marked as the repository's latest, so `gh release view` with no tag still gives the newest `atelier` release, and its notes list the items merged since the previous extension tag that changed `t3-extension/`; the first release, which has no previous tag, lists those merged since the import.
- [x] The workflow refuses, before publishing anything, a tag whose commit is not on `master`.
- [x] The step that finds the tested commit is a script with a test beside it, run in CI by the `changes` job as `scripts/ci-jobs.test.sh` is, so it runs on every change. The test covers: a tag on the merge that changed the extension; a tag two records-only merges later, which is accepted; a tag after a merge that changed `crates/atelier-desk` and whose run failed, which is refused; and a tested commit whose run skipped the job, which is refused.
- [x] The workflow builds the bundle as a run's artifact and publishes nothing in two cases: on a pull request that changes the workflow or `t3-extension/`, and when started by hand on `master`. GitHub starts a workflow by hand only once it is on the default branch, so the Report links the pull request's run, and the planner's thread makes the run on `master` after the merge. The Report shows the bundle's files equal `t3-extension/` at that commit and its installer installing into an empty home directory on the Linux runner, with a stand-in for T3 Code's app named by an option or variable the installer documents, since `install.py` stops when it finds no T3 Code and reads a macOS app's `Info.plist` on anything but Windows.
- [x] The `atelier` release does not run for an extension tag: the tag pattern or `dist`'s configuration excludes it, `release.yml` is regenerated by `dist` and not edited by hand unless the Report says why that was the only way, and `dist plan --tag=t3-extension-v0.1.1` plans no `atelier` release. A tag `v0.7.1` still plans one.
- [x] `t3-extension/README.md` says how a release is made, in one command, and `docs/design.md` says the extension has its own tags and why.

## Scope

In: `.github/workflows/`, `scripts/`, `dist-workspace.toml`, `t3-extension/`, `docs/design.md`.

Out: pushing a real tag, which the planner's thread does after this merges; how a device finds and applies a release (atelier-wlyn).

## Context

`.github/workflows/release.yml` is generated by `dist` 0.33.1 and runs on any tag matching `**[0-9]+.[0-9]+.[0-9]+*`, so an extension tag would start it as things stand. `v0.7.0` is the newest `atelier` release; its build took three and a half minutes.

## Report

A tag `t3-extension-v<x.y.z>` on a merge of `master` now publishes the extension as one zip and its checksum, and the `atelier` release no longer starts for it. To release: `git fetch origin && git push origin origin/master:refs/tags/t3-extension-v0.1.1`.

What changed:

- `.github/workflows/t3-extension-release.yml` runs on a push of a tag matching `t3-extension-v[0-9]+.[0-9]+.[0-9]+`, on a pull request that changes the workflow, `scripts/t3-extension-release.sh` or `t3-extension/**`, and by hand. Its `bundle` job reads the version from the tag (and checks it is exactly three numbers), runs `scripts/t3-extension-release.sh check HEAD origin/master` on a tag push only, then `bundle` and `verify`, and uploads `dist/` as the run's artifact. The `publish` job runs only on a tag push, after `bundle` passed, and runs `gh release create "$TAG" dist/* --verify-tag --latest=false --notes-file notes.md`. Started by hand or on a pull request, `github.ref_type` is not `tag`, so neither `check` nor `publish` runs and nothing is published. The `bundle` job has `contents: read` and `actions: read`; only `publish` has `contents: write`.
- `scripts/t3-extension-release.sh` holds the steps:
  - `check <commit> <master>` refuses a commit that is not on `master`'s first-parent history. This is stricter than "on master": a commit from an item's branch is on master but is not a merge, and CI never ran on master for it. It then walks `git rev-list --first-parent <commit>` and runs `scripts/ci-jobs.sh <candidate>^1 <candidate>` on each, which is what CI compares on a push to master, and stops at the first that prints `extension=true`. That is the tested commit. The path rule is read from `ci-jobs.sh`, not copied. If `ci-jobs.sh` fails or prints no `extension=` line, it refuses rather than moving on to an older commit. It then asks GitHub (`gh api .../actions/runs?head_sha=<tested>&event=push`) for the CI workflow's runs on that commit and accepts only a run that is `completed` with conclusion `success` and whose `extension` job concluded `success`. A run in progress, a failed run, a skipped job or no run at all is refused with a message naming the run, and the message says to re-run the workflow once CI passes.
  - `notes <tag>` lists the `Merge <item>: <title>` commits on the first-parent history that changed `t3-extension/`, since the previous `t3-extension-v*` tag (`git describe --first-parent`). For the first release it lists those since the import and leaves out the import merge itself, the oldest commit that changed `t3-extension/`, as the Done when line says "since the import". On `master` today that is only atelier-7tg6.
  - `bundle <version> <dir>` writes `t3-extension-<version>.zip`, holding `git archive HEAD:t3-extension` under `t3-extension-<version>/` plus a `VERSION` file, and `t3-extension-<version>.zip.sha256` in `sha256sum` format. The zip is made with Python's `zipfile`, since `zip` is not on every host; Explorer and the `tar` in Windows and macOS open it.
  - `verify <zip> <version>` checks the checksum, unpacks the zip, and compares its files with `git archive HEAD:t3-extension` plus `VERSION` using `diff -r`. It then makes a stand-in `T3 Code.app` (an `Info.plist` naming an executable that runs `node`), runs the bundle's `install.py --home <empty>/T3 Custom --app <stand-in>`, and runs the installed `t3-custom check`, which must report `valid` and `release` equal to the version.
- `scripts/t3-extension-release.test.sh` builds a scratch repository whose `master` is a line of `--no-ff` merges and answers `gh api` from fixtures through a stand-in `gh` that applies the real `--jq` expressions with `jq`. Its 12 cases: a tag on the merge that changed the extension (accepted); a tag two records-only merges later (accepted, tested commit is the extension merge); a tag on a merge that changed only `crates/atelier-core` and whose run failed (accepted on the earlier extension merge); a tag after a merge that changed `crates/atelier-desk` and whose run failed (refused); a tested commit whose run skipped the job (refused); a run in progress and a commit with no run (refused); a commit not on master and a branch commit merged into master (refused); the notes for a first release and for one after a previous tag; and the bundle's files and checksum. Each refusal is checked for its reason, which caught a real bug: `grep -q` in a pipe under `pipefail` made every first-parent check fail for the wrong reason. CI's `changes` job runs it after `scripts/ci-jobs.test.sh`.
- `dist-workspace.toml` sets `tag-namespace = "v"`, so `dist` triggers its release only on `v**[0-9]+.[0-9]+.[0-9]+*`. `dist generate --mode=ci` writes the workflow as `.github/workflows/v-release.yml` under that setting; its only other change from `release.yml` is the trigger. I deleted `release.yml` by hand, because `dist` does not remove the old file, and `dist generate --mode=ci --check` passes. `scripts/ci-jobs.test.sh`'s `other-workflow` case names `v-release.yml`.
- `t3-extension/install.py` takes `--app <path>`, documented in its docstring and the README, which names T3 Code's app and writes it to `appPath` in `config.json`. It copies the bundle's `VERSION` into the install folder, and removes a stale one when installing from a checkout. `t3-custom.mjs` reads it: `check` prints `release`, and the daemon's state, which `status` returns whole, holds it. With no `VERSION` it reports `development`. Nothing else in the extension changed.
- `t3-extension/README.md` has a `## Releases` section with the one command, and describes `--app` and `VERSION`. `docs/design.md` has a decision row: the extension has its own tags because it changes more often than `atelier` and a device should not need a clone of a Rust project; the release trusts CI's run instead of repeating it.
