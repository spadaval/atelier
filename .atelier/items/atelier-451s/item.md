## Goal

Let the extension be released as often as it changes, without releasing
`atelier`. Sumeet wants a bundle a device downloads, published from a tag of
its own.

## Done when

- [ ] A workflow publishes a GitHub release when a tag `t3-extension-v<version>` is pushed, where `<version>` is three numbers. It builds no Rust and runs no test itself: before publishing it finds the tested commit and refuses the tag unless that commit's CI run concluded success with the extension's job run in it and not skipped. The tested commit is the newest commit on `master`'s first-parent history, at or before the tagged one, that changes a path the extension's job runs for, by the rule in `scripts/ci-jobs.sh`. On `master` CI compares each merge with the one before it, so a later merge that touches none of those paths skips the job; such a merge changes nothing the job tests, and a tag on it is accepted on the strength of the tested commit. The workflow reads the rule from `scripts/ci-jobs.sh` and does not keep a second copy of the path list. It builds one bundle holding the extension's files and its installer, and attaches the bundle and its SHA-256 checksum. The bundle carries its version in a file the installed extension reads.
- [ ] The release is not marked as the repository's latest, so `gh release view` with no tag still gives the newest `atelier` release, and its notes list the items merged since the previous extension tag that changed `t3-extension/`.
- [ ] The workflow refuses, before publishing anything, a tag whose commit is not on `master`.
- [ ] A test of the step that finds the tested commit covers: a tag on the merge that changed the extension; a tag two records-only merges later, which is accepted; a tag after a merge that changed `crates/atelier-desk` and whose run failed, which is refused; and a tested commit whose run skipped the job, which is refused.
- [ ] The workflow can be started by hand with no tag, on `master`, to build the bundle as a run's artifact and publish nothing. The Report links one such run, and shows the bundle's files equal `t3-extension/` at that commit and its installer installing into an empty home directory on the Linux runner, with a stand-in for T3 Code's app named by an option or variable the installer documents, since `install.py` stops when it finds no T3 Code and reads a macOS app's `Info.plist` on anything but Windows.
- [ ] The `atelier` release does not run for an extension tag: the tag pattern or `dist`'s configuration excludes it, `release.yml` is regenerated by `dist` and not edited by hand unless the Report says why that was the only way, and `dist plan --tag=t3-extension-v0.1.1` plans no `atelier` release. A tag `v0.7.1` still plans one.
- [ ] `t3-extension/README.md` says how a release is made, in one command, and `docs/design.md` says the extension has its own tags and why.

## Scope

In: `.github/workflows/`, `dist-workspace.toml`, `t3-extension/`, `docs/design.md`.

Out: pushing a real tag, which the planner's thread does after this merges; how a device finds and applies a release (atelier-wlyn).

## Context

`.github/workflows/release.yml` is generated by `dist` 0.33.1 and runs on any tag matching `**[0-9]+.[0-9]+.[0-9]+*`, so an extension tag would start it as things stand. `v0.7.0` is the newest `atelier` release; its build took three and a half minutes.
