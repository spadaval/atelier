## Finding 1: Discover new records in the current checkout before looking them up
Recommendation: fix now

`crates/atelier-app/src/repo.rs:391-407` discovers touched record IDs only
from the committed `base...tip` diff. Both `all` and `find` rely on that
set before `read` gets a chance to read checkout files. Consequently a
new, uncommitted record on the current backlog or mission branch is absent
from the reader, even when that branch already has unmerged commits.

I reproduced this on `backlog/tidy` after committing a change to an existing
item. `atelier new "Uncommitted item"` successfully created demo-3pbk;
`atelier list --proposed` omitted it, and `atelier show demo-3pbk` exited 1
claiming no such item or mission existed. Committing the new record made
both commands find it. The Report acknowledges this limitation, but it
contradicts the specified checkout-files exception in the copy-selection
rules and the Done when requirement that `show` find a record wherever it
is. It affects the normal interval after `new`, which intentionally writes
without committing.

Include current-checkout changed and untracked record paths in discovery
when the repository was not opened committed-only. Test a new record on an
already-unmerged backlog branch, without a commit, through both `list` and
`show`.

## Finding 2: Do not advertise proposed items as startable before their branch merges
Recommendation: fix now

`crates/atelier-app/src/view.rs:401-406` sets `Entry::proposed`, but leaves
its startability unchanged. `Entry::startable` in
`crates/atelier-app/src/work.rs:29-30` tests only ready status and unmet
conditions. A ready item that exists only on a backlog branch therefore
passes `list --proposed --ready` and is described as "can start now" by
both `list` and `show`, even though acts intentionally use `Repo::locate`
and cannot start that item.

In the same scratch repository, I filled the new item's sections, ran
`atelier ready demo-3pbk --by planner`, and committed on `backlog/tidy`.
`list --proposed --ready` printed
`demo-3pbk (ready, medium, can start now, on backlog/tidy)`, and `show`
printed `Status: ready, can start now`. Immediately running
`atelier start demo-3pbk` exited 1 because it was absent from the base and
its own branch. The explicit overview-only exclusion of proposed items
does not fix the other views or the ready filter.

Make startability and the standing text account for proposed items, while
keeping the acts' base/own-branch boundary. Add a test using a ready item
filed on an unmerged backlog branch, covering `list --ready`,
`list --proposed --ready`, `show`, and the refusal from `start`.

## Finding 3: Apply the narrowing flags to proposed record changes as well as additions
Recommendation: fix now

`crates/atelier-cli/src/views.rs:117-138` filters proposed record changes
only by mission and label. Items never pass through the ready, blocked,
needs-human or mine predicates used for the other list entries, and mission
changes ignore `--mine`. These flags are accepted together with
`--proposed` and documented to narrow what is shown.

I committed a title-only change to an unheld draft item, demo-ab12, on
`backlog/tidy`. Both `atelier list --proposed --mine` and
`atelier list --proposed --ready` still printed its proposed change,
although the caller held no role on it and the item was draft on both the
base and branch. The proposed additions correctly use the shared grouping
filter; only the separate record-change section leaks these records.

Apply the corresponding narrowing predicates to record changes before
rendering them. Cover at least an unheld draft item's change with
`--proposed --mine` and `--proposed --ready`, plus the needs-human and
blocked flags.
