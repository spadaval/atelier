## Finding 1: Include passed rules from commits that produce no inferred log action
Recommendation: fix now

`crates/atelier-cli/src/views.rs:59-66` builds the entire section from `history.actions`. That is not a list of all commits carrying skips. `crates/atelier-core/src/log.rs:583-604` retains a commit's trailers only inside the loop over inferred actions, so a commit with no inferred action disappears together with its rules.

Two successful CLI operations reproduce this with the reviewed binary:

- Create and commit a proposed mission on its named branch, then run `ATELIER_SKIP="Lead accepts this plan without two reviews" atelier merge` as its planner. The merge succeeds and its message contains `Atelier-Merge: demo-m1ss`, the two-review rule and reason, and `Atelier-Skip-By: p1`. After the merge, `atelier show demo-m1ss` prints an agreed mission with no `Rules passed:` section, and `atelier log demo-m1ss` is empty. `Walker::merge` at `crates/atelier-core/src/log.rs:616-622` looks only for an item record, so it never emits the mission's merge.
- On an agreed mission, start an item, then use a backlog branch from the base to run `ATELIER_SKIP="Change the active item priority" atelier set demo-ab12 --priority low`. Execute its printed Git command and let that commit reach the base. The commit records the rule that the item must be draft or ready, its reason and `p1`; both the mission page and log omit it because a priority change generates no action. This is also the path already exercised by `skip::set_with_a_skip_changes_a_started_items_base_record`.

Both are commits of the mission or its items, so omitting their rules fails Done when 2. Preserve trailer-bearing commits even when action inference yields nothing, and cover both the mission merge and field-only change in the mission page and log tests.

## Finding 2: Read passed rules while a mission is still proposed on its branch
Recommendation: fix now

At `crates/atelier-cli/src/views.rs:60`, a `None` history result becomes an empty list of passed rules even though `mission_view` has already found the mission. The lookup in `crates/atelier-core/src/log.rs:220-231` checks a branch for an item record but checks for a mission record only on the base.

Reproduced with a mission committed only on `demo-m1ss`: run `ATELIER_SKIP="Lead this proposed plan now" atelier lead demo-m1ss` as `lead1`, then execute its printed Git command. The commit has both skip trailers. Unfiltered `atelier log` correctly shows the lead action, rule, reason and `(by lead1)`. However, `atelier show demo-m1ss` finds the proposed mission and displays `Lead: lead1` with no `Rules passed:` section; `atelier log demo-m1ss` refuses with “No item or mission demo-m1ss ... on a branch named demo-m1ss.”

The Report acknowledges the underlying lookup defect, but the new mission section depends on it and Done when 2 does not exclude proposed missions. Resolve mission history from its named branch as well as the base, and add a proposed-mission fixture proving that its page and filtered log show the recorded departure.
