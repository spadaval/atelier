## Finding 1: Keep an unconfirmed pull-request close from becoming a completed stop
Recommendation: fix now
Was: 3-lb05.1
Response: fixed in 7ec7459
Now: kept

The new pre-stop CLOSED regression passes after the act returns. However,
`Fetches::forget` at `crates/atelier-desk/src/fetch.rs:99-103` only removes
the branch from the map. It leaves `forge_error` clear after a successful
previous poll, so `pull_request` at line 124 returns `Known(None)`, not
`Unknown`, until the following forge read finishes. `server.rs:119-123`
exposes this interval to concurrent readers; the acting mutex excludes
other acts, not page reads.

I first cached the plan's OPEN pull request, then made `gh pr close` fail
and held the follow-up `gh pr list` on a FIFO. While that list was in
progress, the detail and both mission lists returned
`(stopped, false, true)`, instead of `(stop_pending, true, false)`. Releasing
the FIFO let the failed list finish and the act correctly report that its
pull request was not closed. The page had already certified a stop with
an unclosed PR. A slow or stalled forge makes this false completed state
last for the duration of the refresh.

Invalidation also only runs for a Desk act. In a second test I cached a
CLOSED pull request while the plan was still proposed, then wrote the drop
through `drop_mission` in the planner's clone and pushed it, modeling the
PR having reopened and the forge becoming unavailable. The next
`fetch_all` fetched the new drop but its PR read failed. The old CLOSED
entry remained known at `fetch.rs:121`, and the detail and both lists again
returned `(stopped, false, true)`. There was no confirmation of closure
after this drop, and no later failed-refresh return corrects this case.

Keep invalidated pull-request state explicitly unknown until a fresh read
confirms closure or absence, including while that read is in progress.
Qualify closure by the drop it confirms so a newly observed drop from
another clone cannot inherit a pre-drop CLOSED cache entry. Preserve the
existing test where closure was confirmed after the drop and a later,
unrelated outage does not undo that confirmation. Cover concurrent reads
during refresh and an externally pushed new drop across the detail and
both mission lists.
