## Finding 1: Keep an unconfirmed pull-request close from becoming a completed stop
Recommendation: fix now
Was: 2-2zhl.2
Response: fixed in 8a14c2e
Now: kept

The successful-empty-list regression now passes, but a previously CLOSED
entry still certifies a later stop even when its close and follow-up read
fail. `crates/atelier-desk/src/fetch.rs:111` returns any cached PR entry as
known despite `forge_error`; `read.rs:218` accepts its CLOSED state as
confirmation that the new stop is published.

I cached a CLOSED PR while the plan was still open, then modeled it being
reopened between polls and the forge becoming unavailable before the stop.
Both `gh pr close` and the follow-up `gh pr list` failed. The act correctly
said its pull request was not closed, but `shown` returned
`(stopped, false, true)`: the detail said stopped, the active list omitted
it and the completed list included it. The required result is
`(stop_pending, true, false)`. This differs from the existing CLOSED-then-
failed-read test, which confirms closure after the drop and then loses
connectivity.

A cached closed PR from before a new drop does not confirm that stop's
publication. Invalidate or qualify that confirmation when the close fails,
and keep the new stop pending until closure or absence is established.
Preserve the existing behavior for a stop already confirmed complete before
an unrelated later outage. Add the pre-stop CLOSED cache regression across
the detail and both mission lists.

## Finding 4: Attribute a pending drop to the branch that actually drops the mission
Recommendation: fix now

`crates/atelier-desk/src/read.rs:794` turns every agreed mission with both a
source branch and `StopPending` into a synthetic drop on that source. But
`StopPending` can come from a different branch's stop. Line 803 also then
omits the genuine own-branch amendment because the overall mission state
is no longer Open.

I created an agreed `demo-aaaa`, pushed an amendment of its Why on
`demo-aaaa`, and pushed its drop separately on `backlog/stop-demo-aaaa`.
The mission page correctly named `origin/backlog/stop-demo-aaaa` in
`stop_on`. `/api/proposed` instead listed TWO dropped changes for that
mission, one on each branch, and omitted the amendment from plans. The
`origin/demo-aaaa` record is still open and contains only the amendment, so
its displayed drop is false and its plan-review information is lost.

Derive the own-branch change from that branch's actual record rather than
the mission's aggregate pending state. Keep the amendment listed with its
review information while listing the separate branch's real drop. Cover
both proposals together in one regression.
