docs/product/workflow-configuration.md:34-37 and crates/atelier-cli/src/commands/session.rs (the 'Installing Atelier' guidance, 'a pull request or a reviewed merge') together with crates/atelier-cli/src/commands/git.rs (install exemption in check_base_commits): the documented local-merge path refuses when Git fast-forwards. Since 191c8574, the install is the first commit on the first-parent line that adds the policy, plus what that commit merges in. A plain git merge of an install branch onto a base that has not moved fast-forwards, so there is no merge commit. The init commit becomes the install, and every later commit on the branch is checked one by one. Reproduced in /tmp/rv40i6/d: chore/atelier-tracker holds an init commit plus a review-fix commit that changes AGENTS.md (astromech's branch has the same shape). git switch main && git merge chore/atelier-tracker fast-forwards, and land on main fails with land_base_unreviewed on the AGENTS.md commit. Its remedy text says to run git branch -f main main@{upstream}, which throws the install away. With --no-ff the same branch lands ('Base commits: none unpushed outside recorded review'). land runs in the Stop hook, so this is a false refusal on a path the docs and the land guidance both name. Smallest fix: say git merge --no-ff (or a pull request merged on the host, then pull) in the Installing Atelier docs and in the land guidance line, and add the fast-forward case to the test as an expected refusal or covered behavior. Alternative: have check_base_commits treat a fast-forwarded install run as the install, but only if it can tell that run apart from later direct commits, so that atelier-17it does not come back.
