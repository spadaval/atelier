crates/atelier-cli/src/commands/git.rs:170-196 limits each review's coverage to commits after the owner's first workflow_branch commit ('start'). Any work committed on the branch before 'atelier start' recorded the branch is therefore never covered, even after a gated atelier merge. That includes the recovery path that land's own refusal and docs/product/reviews-and-merge.md:121-122 prescribe: git switch -c <type>/<id>, git branch -f <base> <base>@{upstream}, atelier start <id>. Reproduced: direct code commit D on main; land refuses. Follow the advice, close the issue, record an independent approval and atelier merge (passes; merge reviewed D through base...branch). Then land on main fails with 'land_base_unreviewed: commit 2636db38 on main changes app without recorded review ... Move it to a work branch ...', which sends the user round the same loop. The same applies to any unowned branch with commits that is later started. This is a false refusal in the Stop hook after a legitimate merge. Suggested fix: bound the range by what was on the base when the branch forked, not by the start commit. For example, use 'rev-list <pin> --not <upstream> <merge-base of started and upstream>', or just '--not <upstream>'. The start^ bound adds nothing, because start now refuses to branch from a base with uncovered commits, and pushed_done already rules out re-crediting integrated owners. Add a test that follows the recovery advice through merge and land.
