# next-loop: a fresh agent through the new binary's loop (2026-11-10)

Item atelier-67nn, mission atelier-fcb7, criterion `fresh-agent-loop`. A fresh
agent with no skill and no instructions, given only "Run `atelier status` and
do what it says.", took one ready item to done with a reviewer that was
another thread, on Claude Opus and on Codex.

**Result.** The final round passed: three runs on Claude Opus 5.5 and three
on Codex (`gpt-6.1-sol`), each graded pass, with at most one refused or
errored `atelier` call per run (five runs had none, one had one). Getting
there took two rounds of wording changes. Round 1's Codex run failed: it read
`submit`'s handoff line as its own next command, ran `atelier review`, was
refused, and stopped.

## Setup

- **Fixture** (`scenarios/next-loop/setup.sh`): a Python repository on
  `main` with `slug.py`, one test and an `.atelier/` of the new layout. Its
  `config.toml` names no forge and one merge check, `python3 -m unittest -q`.
  One item, `slug-k3fa`, is `ready`: make `slugify` collapse runs of
  punctuation into one hyphen and trim the ends, with a test for each of two
  examples. `work/bin/atelier` is a copy of the round's binary
  (`next/target/debug/atelier`, copied once per round), first on `PATH`.
  There is no `AGENTS.md`, skill or other instruction.
- **Prompt:** `Run \`atelier status\` and do what it says.`
- **Isolation.** Claude Code as the harness already runs it. Codex runs with
  `HOME` and `CODEX_HOME` inside the work directory, under `/var/tmp`, so
  neither `~/.codex` nor `~/.agents/skills` loads; the host's sign-in is
  linked in and the link removed when the run ends. Codex's own bundled
  system skills (`imagegen`, `skill-creator`, `skill-installer`,
  `openai-docs`, `review-agent`) still load, as they do anywhere. The
  isolation canary passed before every batch, on Haiku for Claude and
  `gpt-6-luna` for Codex.
- **Models.** Claude: `claude-opus-5-5` at the harness's `--effort high`.
  Codex: `gpt-6.1-sol` at Codex's default effort. Child threads run the same
  model as their parent.

### How the reviewer was started

The tool identifies a thread by `T3CODE_THREAD_ID`, else the harness's
session ID. Before writing the harness I checked what identity a harness's
own subagent gets:

| Harness | Subagent | What it sees |
| --- | --- | --- |
| Claude Code 2.1.321, headless (`claude -p`) | `Agent` tool | The parent's `CLAUDE_CODE_SESSION_ID`; no `T3CODE_THREAD_ID` |
| Claude Code 2.1.321 under T3 Code | `Agent` tool | The parent's `CLAUDE_CODE_SESSION_ID` and the parent's `T3CODE_THREAD_ID` |
| Codex 0.167, headless (`codex exec`) | `spawn_agent` | The parent's `CODEX_SESSION_ID`, its own `CODEX_THREAD_ID` |

So a native subagent is its parent to Atelier, and is refused as the
reviewer of its parent's item. No wording can fix that. Codex does give a
child its own `CODEX_THREAD_ID`, which Atelier does not read. Under T3 Code,
only a thread T3 starts (`delegate_task`) gets an identity of its own.

The harness therefore stands in for T3 Code (`"threads": true` in
`scenario.json`): each agent it starts gets its own `T3CODE_THREAD_ID`, and
`work/bin/delegate "<task>"` (`harness/delegate.py`) starts a fresh agent of
the same kind and model as a new thread in the caller's directory, waits for
it, and prints its final reply, as `delegate_task` with `mode: "wait"` does.
The system prompt (Claude `--append-system-prompt`, Codex
`developer_instructions`) describes the tool and nothing else:

> Agents here run as threads, each with its own thread ID in
> T3CODE_THREAD_ID. To start another agent as a new thread, run
> `delegate "<task>"` in a shell: it starts a fresh agent of your kind in the
> current directory with that task as its only prompt, waits for it to
> finish, and prints its final reply.

It does not say when to use it, and it does not mention review. The native
subagent tools stayed available; no agent used one. In every run, the
reviewer was a `delegate` thread started by the implementer.

### Grading

`grade.py` checks the state on `main`: the item's record says `done` and
came in an Atelier merge (`Atelier-Merge:` trailer); a review file approves
it and none of its reviewers is among the item's implementers; and on
`main`'s tree the suite passes, both Done when examples hold, and the tests
fail when `slug.py` is put back to the original. It counts each `atelier`
invocation in the run's transcript and each delegated thread's, from what
the shell executes: Codex's `bash -lc` wrapper unwrapped, quoted text and
heredoc bodies left out, command substitutions kept. So
`delegate "Run atelier review x"` runs none and `atelier merge; atelier
status` runs two. Refusals and errors are counted from Atelier's own refusal
and error text in the output, at most one per invocation, not from exit
codes, which a shell, a pipeline or a command substitution can hide (round 2
showed one). A fixture drives the real binary to each kind of refusal and to
each successful command, so the patterns follow the wording.

Its fixtures (`python3 -m unittest` in the scenario directory, with
`NEXT_ATELIER` set) drive the real binary and show it failing a run where
the item is approved but not merged, where the approving review lists the
implementer among its reviewers, where the tests pass on the old code, and
where a test fails on `main`; and passing the plain path. Two more check the
counts on Claude and Codex transcripts, including refusals an enclosing
shell hid (`atelier submit; atelier submit; true`) and task text that runs
nothing.

## Fumbles and what changed

### Round 1 (binary 81539b4, the step A commands as merged)

**Codex 4997: ran the handoff itself, was refused, and stopped.** After
`submit` printed

```text
Submitted slug-k3fa for review.
Start a reviewer with: Run `atelier review slug-k3fa` and follow what it prints.
```

it said "Atelier has accepted the submission and instructed me to run its
review step", ran `atelier review slug-k3fa`, and got

```text
You (thread thread-c2fa61c6) have implemented slug-k3fa, and an author does not review its own work. Nothing changed.
If no reviewer is working on it, start one with: Run `atelier review slug-k3fa` and follow what it prints.
What a reviewer is shown:
...
```

It ended the run there: "Atelier requires a separate reviewer; it rejected
self-review." It never used `delegate`. Neither message said the reviewer
must be another thread or how to start one.

**Codex 4997: submitted with its code uncommitted.** It edited `slug.py` and
`test_slug.py`, ticked the item and ran `atelier submit` without
`git commit`. `submit` commits only the item's directory, so the commit
under review held no code. Nothing said so. Not a refused call.

**Claude 1ca1** ran `atelier --help` and `atelier submit --help`; its
implementer committed before submitting. No failed call.

Changed for round 2 (commit f7053ac):

- `submit`'s handoff, the author's `review` refusal, and the implementer's
  `status` while no review is open now say: "A reviewer must be another
  thread: not you, and not a subagent of yours, which runs as your thread.
  Start one with your harness's tool for a new agent thread, and give it this
  task: ... Then wait for its verdict, and run `atelier status`."
- `status` and a refused `submit` say "`atelier submit` commits only the
  item's directory, so commit your change first." `status` lists the paths
  not committed; `submit` names any it left out.
- While the item is in review, the implementer's `status` names the thread
  holding the round's review ("Thread X holds this round's review. Wait for
  its verdict, then run `atelier status`."), the risk the brief named.
- A thread that reviewed the item is no longer pointed at
  `atelier start <id>` by `status` or by `review` after its verdict, the
  other risk the brief named: `acts::next` offers it nothing, and it is told
  "Your review is done, and nothing on this item is yours to do."
- A visitor on someone's branch reads "Only if you mean to take it over from
  its holder: atelier start <id>" instead of "Then: atelier start <id>".

## Limits

- **One happy path.** Every reviewer approved in round 1 of review, so no
  run exercised `verdict changes`, findings, Responses or a second round. The
  scenario shows agents find their way through the plain loop; it says
  nothing yet about the changes-requested loop, where the brief and `status`
  carry the most text.
- **`delegate` stands in for T3 Code** and is described in the system
  prompt, as T3 describes `delegate_task` in its tools. Under real T3 Code, a
  Claude agent's guidance prefers its native `Agent` tool for a child on the
  same provider, and that child would be refused as the reviewer. The new
  handoff text names that case, and an agent should recover with one
  refusal, but no run tested it.
- The fixture is small; on a larger change agents may commit, tick and
  report differently.
- The single-line `status` view of a Done when line that wraps shows only its
  first line ("returns `hello-world`, and"). No agent was confused by it;
  every agent read the item file.

## Rerun

From a checkout at the final commit, with the binary built:

```bash
mkdir -p ~/.cache/next-loop/bin && cp next/target/debug/atelier ~/.cache/next-loop/bin/
for agent_model in "claude claude-opus-5-5" "codex gpt-6.1-sol"; do
  set -- $agent_model
  NEXT_ATELIER=~/.cache/next-loop/bin/atelier python3 evals/agent-factory/harness/run.py \
    next-loop --agent $1 --arms none --runs 3 --model $2 --jobs 3 \
    --out ~/.cache/next-loop/runs-$1
done
```
